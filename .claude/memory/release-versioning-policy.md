isabelle-query versioning: as of 2026-06-08 the project is still in alpha with few/no third-party users, so breaking CLI changes are acceptable and do NOT require a major (or even minor) bump — patch bumps are fine. Precedent: v0.2.1 and v0.2.2 each shipped breaking CLI changes as patch releases. Once the CLI settles down, switch to proper SemVer: breaking changes go in **major** releases.

**Why:** no downstream consumers to protect yet, so the cost of a break is ~zero; the constraint only bites once people pin the version. The maintainer is effectively the only consumer for now (see [[user-andras-salamon]]).

**How to apply:** within alpha, the bump size now signals *intent to highlight*, not strict SemVer. Additive features and refinements to a freshly-shipped surface are **patch** bumps. A change that **breaks an established expectation and should stand out in the notes** gets a **minor** (0.x.0) bump — the user's call, made explicit. Precedent (2026-06-11): `[enclosing]` range mode + locus round-trip shipped as **0.2.7** (additive/refinement → patch); the batch containing the span render change `-`→`..` (breaks `[src A-B]`/`outline`/`largest` output expectations) was deliberately slated as **0.3.0** so the break is highlighted, with the user saying "since 2 breaks some expectations and that needs to be highlighted." Precedent (2026-07-01): the two upstream-filed bug fixes `[function-defs]` (index `function` defs — adds call-graph nodes) + `[src-doc-attribution]` (leading-doc span attribution — shifts `enclosing`/`outline`/`largest`/`[src …]`) shipped as **0.4.0**, a **minor** bump, on the user's explicit call that "the changes are major enough" — even though neither is strictly *breaking* (both are additive/correctness). So the minor-bump trigger is "substantive, output-shifting, worth standing out," not only backward-incompatible. Still no push for a *major* bump in alpha; re-evaluate major-for-breaking when the user signals the CLI has stabilised (likely around 1.0).

**Release mechanics** (final design, 2026-06-11): release notes come from the **version-bump commit's message** — write the changelog there (e.g. `git commit -m "0.2.6 - changes from 0.2.5" -m "## Added" -m "- ..."`). `make release` reads the version from pyproject.toml, tags HEAD plainly (`git tag -a "$TAG" -m "isabelle-query $VERSION"` — the tag message is just a label, NOT the notes), warns if HEAD's message is a bare one-liner, and pushes branch + tag. `.github/workflows/release.yml` fires on the `v*` tag push and publishes the Release by reading the **tagged commit's message** via `gh api repos/.../commits/$TAG --jq .commit.message` and passing it to `gh release create/edit` (idempotent: edits if the Release exists, else creates) — all on the runner, no local `gh`/web (both of which the user finds high-friction).

Why commit-message-and-API, not the tag annotation: the earlier `gh release create --notes-from-tag` reads the *local* tag, which on the runner is lightweight, so it silently fell back to the tagged commit's message — this gave v0.2.5 a sparse one-line body. Reading the commit message via the API is deterministic and avoids it.

Gotchas: (1) the workflow runs as it exists in the tagged commit, so it must be on main *before* tagging. (2) The repo's "Workflow permissions" default is the restricted "Read repository contents and packages permissions" — fine and need not change; the workflow's own `permissions: contents: write` overrides it (least-privilege). Only flip to "Read and write permissions" if a run 403s, then "Re-run failed jobs". (3) v0.2.5 was the last release before this design and kept its bare `build: bump version to 0.2.5` body (a one-time web edit is the only non-force way to fix an already-published body; the user chose to leave it). **The commit-message flow is now proven** — v0.2.6 and v0.2.7 both published with their full changelog bodies rendered (verified via the public releases API, since local `gh` is unavailable: `curl -s https://api.github.com/repos/ott2/isabelle-query/releases/tags/$TAG`). A quick post-release API check is still worth doing, but the mechanism is no longer unproven.

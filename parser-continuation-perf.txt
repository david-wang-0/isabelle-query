DESIGN (the "tiny state engine" the user described — first vs continuation line):
  After `name = _parse_name(rest)` (or _parse_typedecl_name), if it is "?" AND
  `rest` carries no usable name token, PEEK FORWARD past blank / `\<comment>` /
  `text` lines to the next non-blank line and parse the name from THERE with the
  same _parse_name / _parse_typedecl_name. Do NOT consume that line — the body
  scan still includes it; just adopt its name. Keep decl_end_line/spans correct.

TRIGGER precisely (avoid regressions):
  * Only when the same-line name is absent: rest is empty after stripping
    `\s+where$` and the decl prefix, OR _name_from returns "?". Note
    `definition (in foo)\n bar :: ...` strips to "" -> must still look ahead.
  * Bound the lookahead to a few non-blank lines so a malformed file can't run on.
  * Skip leading blank / comment / text lines between keyword and name.
  * Multi-name decls (`inductive A and B`, `definition a and b`) — out of scope;
    keep returning the head name.

TASK 2 — PERFORMANCE TESTS (guard throughput as the parser grows)
--------------------------------------------------------------------------------
WHY: correctness has been added (keyword scanner, text-block skip, per-line
_match_decl table lookup, header pre-scan, name-aware _isa_word_pattern; Task 1
adds lookahead). Fast answers matter as much as accuracy — sometimes fast/approx
beats slow/perfect. We want a guard that catches ORDER-OF-MAGNITUDE regressions
(2-5x), not 10% noise, and forces a conscious tradeoff when a feature slows a
hot path.

BASELINES captured on this machine (whole AFP = 10,084 files / 5.89M lines;
treat as ballpark, machine-relative — NOT as CI thresholds):
    read + splitlines ............ 1.40 s
    header pre-scan (union) ....... 0.25 s   (196 custom commands found)
    extract_entries (with union) .. 3.63 s   (367,013 entries; ~1.62M lines/s)
    extract_entries (empty table) . 3.09 s   (custom-table overhead +18%)
    load_index (full) ............. 5.08 s
    _build_call_graph ............ 21.78 s   (V=160,092 names, E=2,891,018 edges)
    _transitive_closure (BFS) ..... 0.139 s  (156,517 reached from a hub seed)
    end-to-end `callers -r` ...... 27.00 s

KEY FINDING — target the right thing: the RECURSIVE DAG TRAVERSAL queries
(`callers -r`, `uses -r`, `callees -r`, the `unused` cascade) cost ~27 s, and
**81% of that is `_build_call_graph` (21.8 s), not the traversal**. The BFS
`_transitive_closure` is already O(V+E) and negligible (0.14 s over 2.9M edges).
So the perf guard belongs primarily on `_build_call_graph` throughput; the BFS
needs only a sanity check that it stays linear (not accidentally O(V^2)).
(Functions: `_build_call_graph` ~line 1005, `_transitive_closure` ~1087,
`cmd_callers`/`cmd_callees`/`cmd_unused` use them; grep to confirm.)

GRAPH-BUILD PROFILE — the 22 s is EDGE DISCOVERY, not graph code. Do NOT add
networkx (or any graph lib): 0% of the cost is adjacency storage (a trivial
dict[str,set]) or traversal (BFS, already 0.14 s); loading 2.9M edges into a
DiGraph would be SLOWER and break the zero-dependency design. cProfile of
_build_call_graph (tottime):
    re.findall (x3 token patterns) .. 7.9 s   tokenizing 5.9M lines
    loop body inline ............... 12.9 s   candidate-set building / driving
    _entry_at_line (binary search) .. 5.5 s   line->owning-entry, 2.6M calls
    `any(line_no in r ...)` @1060 ... 3.9 s   text-range exclusion, 64.5M genexpr
    set.intersection / .add ......... 3.8 s
Decomposition measured:
    tokenize + hash-intersect FLOOR  11.5 s   (irreducible: must read every line)
      one regex pass ................ 6.7 s
      2nd/3rd passes add ............ 4.8 s
    => ~10 s of overhead is REDUCIBLE (attribution + exclusion + dict ops).
NB: the name MATCHING is already a hash (`name_set.intersection(tokens)`, ~1.9 s)
-- the old O(lines x names) scan is long gone. The residual scan is tokenisation.
STDLIB OPTIMISATION LEVERS (no dependency), realistic 22 s -> ~10-12 s:
  1. One combined tokeniser pass, not three findall()s  (~ -4.8 s).
  2. Linear line->entry attribution (advance a pointer; lines and entries are
     both sorted) instead of 2.6M binary searches  (~ -4-5 s).
  3. Precompute per-theory exclusion sets (text-range + def-site) as O(1) `in set`
     lookups instead of `any(line_no in r for r in ranges)`  (measured -12%).
  4. BIGGEST: the corpus is tokenised TWICE -- once in extract_entries (3.6 s) and
     again here (11.5 s floor). Have the parse pass emit each line's candidate
     tokens so the graph build skips re-tokenisation. Tradeoff: memory + coupling.
  After optimising, the perf test (below) should pin a build-throughput floor and
  prove it fails on a regression.

DESIGN — put it in tests/test_perf.py, two layers:
 (a) Deterministic micro-benchmark (NO corpus; do not read the real AFP — it is
     not vendored). Synthesise a large in-memory theory (~50k lines: a header
     declaring a few custom keywords, then thousands of mixed
     definition/lemma/datatype/custom-command decls with proofs, text blocks,
     and symbolic + special-char names). Time and assert THROUGHPUT FLOORS with
     generous (~3x) headroom:
        - extract_entries: assert >= e.g. 0.5M lines/s (baseline ~1.6M).
        - _build_call_graph: assert >= some entries/s or lines/s floor (this is
          THE hot path — 81% of recursive-query cost).
        - _transitive_closure on a synthetic DAG: assert it stays ~O(V+E)
          (e.g. time grows ~linearly when you double the graph; or just a wide
          ceiling) — catches an accidental quadratic.
     Use time.perf_counter, one warmup, best-of-3 to damp noise. Gate behind an
     env var (e.g. ISABELLE_QUERY_PERF) or mark slow so the default sub-second
     suite stays fast. PRINT the numbers (not just assert) so the trend is visible.
 (b) Optional corpus-scale timing (gated on ISABELLE_QUERY_CORPUS like
     test_corpus): time header pre-scan, extract_entries over the tree,
     load_index, _build_call_graph, and an end-to-end `callers -r`; print a small
     table; assert each under a generous budget.

DESIGN NOTES:
  * Assert FLOORS/CEILINGS with WIDE margins — machine variance is real; the goal
    is catching 2-5x regressions, not micro-tuning. Always log the actual numbers.
  * Keep the empty-table fast path and the union path as separate measurements
    (they differ ~18%), so a regression in either is visible.
  * A RELATIVE invariant is more portable than absolute seconds — e.g. "union
    path within 1.5x of empty path", or "build-graph time within Nx of
    extract_entries time".
  * SELF-CHECK the guard: temporarily inject an O(n^2) stub or time.sleep and
    confirm the perf test FAILS, so you know it actually guards.
